# pi6529 design

_2026-11-07. The design behind the first image (pi6529 0.1.0, validator 0.1.0-rc.10). Written so a builder could plan from it without going back to the owner. Decisions marked **(call)** were made by the builder and can be overturned._

## Intent

6529 wants more validators in more homes. Their validator already runs on a Raspberry Pi 4 or 5 with the 64-bit OS, but a holder who has never run a server must today: install an OS, log in, install a .deb, read a terminal, open an SSH tunnel, and find the right port. pi6529 removes every step a flashable image can remove, and leaves exactly the steps 6529's rules say must stay: the key is made on the device, the authorization is drafted on the device, and only the owner's wallet signs.

The product has three possible forms, in order of leverage:

1. **An image plus a Raspberry Pi Imager entry.** Zero logistics, reaches people who already own a Pi. This is what 0.1.0 ships.
2. **Pre-flashed SD cards or SSDs.** The same image, written for people who won't. A small step up in logistics.
3. **Full kits.** A real small business with support obligations. Out of scope until 6529's first public release.

## Goals

- A holder flashes a card with Raspberry Pi Imager, plugs the Pi in, and inside half an hour has a validator that signs every day.
- The README is readable by someone who has never opened a terminal, and every command in it is copy-paste.
- Every build is pinned and checked: the base OS image and 6529's .deb are fetched by URL and verified against a hash in the repo. The build runs the same on a Mac, a Linux box and in GitHub Actions.
- Nothing device-specific ships in the image: no key, no keystore password, no machine id, no SSH host keys, no validator config. All are made on the device at first boot.
- Updating the validator is one command that respects 6529's rule of no automatic updates: `pi6529 update` shows the notes, asks, verifies the signed release list through the validator's own key, checks the SHA-256, installs.
- The repo is laid out for the next iterations: a pinned config file, a bump script, a check script, a boot-partition settings file, a CLI with room for more commands, a changelog, a roadmap.

## Non-goals (for 0.1.0)

- A web UI of our own. 6529's validator already serves a page; we make it reachable.
- Running an Ethereum node on the Pi. 6529's hardware page says the validator doesn't need one.
- A LAN-exposed page by default. 6529 chose loopback only; we keep it (the config has a `[ui] lan` switch for a later, opt-in iteration).
- Automatic validator upgrades. Against 6529's P36.
- Hardware sales, cases, branding, or anything that could read as 6529's own product.

## Anti-goals (what would make this a failure even if it works)

- **A double vote.** Two Pis signing with one key excludes the owner's account for 30 days and burns that grant's keys forever. Any design where a key could be cloned with the card is a failure. Hence: the image holds no key, the README says "never clone this card" in three places, the data folder carries a CACHEDIR.TAG, and `pi6529` prints the warning in its help.
- **A secret baked into a public image.** The .deb's postinst runs `validator init` during the build and writes a random keystore password. The build wipes the data folder so the first boot makes a fresh one.
- **Looking like 6529.** Independent, unofficial, says so on every page.
- **A mandatory update the day a customer unboxes.** 0.1.0 stops signing on 1 December 2026 and new installs must start before about 23 November. So: prototype now, hold hardware until the first public release.

## Constraints (from 6529's docs, checked 2026-11-07)

- Validator needs glibc ≥ 2.35 → Raspberry Pi OS Bookworm or Trixie, 64-bit. Trixie (glibc 2.41) is current.
- The .deb installs `/usr/bin/validator`, the unit `6529-validator.service` (hardened, `User=validator6529`), data in `/var/lib/6529-validator` (0700). Its postinst runs `validator init --mode home` if no config exists.
- The page and the local API bind to loopback only; the port is random per install unless `--ui-bind` is given. Port 6529 is refused by `init` ("that was every validator's address up to rc.7").
- `validator open --print` needs the service account's files → root. It prints a one-time link with a `?token=`.
- Authorization on a phone: the validator shows a QR to `6529.io/validator/authorize#<draft>`; the owner signs there and pastes the signature back. No server sees the draft.
- The signed release feed is at `6529.io/validator/releases.json` (+ `.sig`); `validator update check --feed FILE --json` verifies it offline with 6529's built-in key. Only the newest release can be downloaded, at `<download_page>/download/<version>/<file>`.
- Test releases have no Sigstore signature; the first public release adds `SHA256SUMS.sigstore.json`.
- A Pi has no battery clock; the validator refuses to sign with a clock off by more than a minute (`CLOCK`).

## Decisions

- **Base: Raspberry Pi OS Lite (64-bit) Trixie, 2026-10-06.** (call) Current, supported, glibc 2.41, cloud-init first-boot customisation from Imager works unchanged.
- **Install method: 6529's own `.deb`, unmodified.** (call) Their postinst, unit and desktop entry stay; the image only adds files beside them. Any future 6529 change to the package flows through a pin bump.
- **Fixed page port 7529 on 127.0.0.1.** (call) So the README's tunnel command is literal. Chosen because 6529 refuses 6529 and 6530 appears in their examples. Changeable in `pi6529.txt`.
- **Keys and config made at first boot by `pi6529-firstboot.service`,** not at build. The validator unit is left disabled in the image and enabled by firstboot after `init` succeeds.
- **Settings file on the boot partition, `pi6529.txt`.** (call) FAT, readable from any computer, read once at first boot. Keys: name, mode, tor, ui_port, country. Later iterations can add more without changing the flow.
- **A `pi6529` helper command** wrapping `validator` as the service account, plus a login welcome that shows status and the link. (call) Users never need to learn `runuser -u validator6529 -- validator ... --data-dir ...`.
- **SSH enabled by default; no default user or password.** Imager's customisation creates the user. A headless box with SSH off is a brick.
- **Wait up to 90 s for NTP before the validator starts** via a drop-in `ExecStartPre`, never failing. (call) Avoids Tor certificate errors right after a cold boot; does not block boot if NTP is unreachable.
- **Unattended Debian security updates on; the validator blacklisted.** (call)
- **Persistent journal capped at 200 MB; Wi-Fi power save off.** (call)
- **No `[ui] lan = true`.** Loopback as 6529 ships it. Roadmap item, opt-in, if 6529 is fine with it.
- **Image versioning is its own:** `VERSION` file (0.1.0) and tag `v0.1.0`, independent of the validator's. The release record on the device (`/etc/pi6529/release`) names both.
- **Repo on GitHub, public** (made public on 2026-11-07 at the owner's request). The Imager entry points at GitHub Releases.
- **License MIT for our files;** the validator is redistributed under Apache 2.0 with NOTICE kept.

## Build pipeline

`make image` → `build/fetch.sh` (hash-checked downloads) → privileged `linux/arm64` Docker container runs `build/inside/customize.sh`: decompress, grow root by 1 GB, loop-mount, chroot, `apt-get install` jq + unattended-upgrades + the .deb, apply `image/rootfs/` overlay, write `/etc/pi6529/release`, wipe device-specific state, run `build/check-image.sh` (26 assertions), zero free space, `xz -6`, write `.sha256`, `SHA256SUMS` and a `.json` with the sizes and hashes the Imager entry needs. `build/imager-entry.sh` turns that into `imager/os_list.json`.

GitHub Actions (`.github/workflows/build-image.yml`): lint on every push; on a `v*` tag, build on `ubuntu-24.04-arm`, attach the image to a Release, and record build provenance. Sigstore blob signing is a roadmap item.

## First-boot sequence on the Pi

1. Stock Raspberry Pi OS: resize root, regenerate SSH host keys, cloud-init applies the Imager settings (user, password, Wi-Fi, hostname if set).
2. `pi6529-firstboot.service` (before the validator): read `pi6529.txt`, ensure the account and folder, `validator init` as `validator6529` with the chosen flags, add the country if given, write `CACHEDIR.TAG`, enable and start `6529-validator.service`, stamp `/var/lib/pi6529/firstboot-done`.
3. `6529-validator.service`: `wait-for-time` up to 90 s, then `validator run`. Tor connects (1–2 min), history downloads (about 20 min), then the page says the next step is the key.
4. Owner: `ssh -L 7529:127.0.0.1:7529 user@pi6529.local`, the welcome prints the one-time link, the page makes the key and drafts the authorization, the phone signs, the signature is pasted back.

## Verified before the first tag

- `make image` passes all 29 checks in `build/check-image.sh`.
- The image's root filesystem was booted under systemd (as a privileged Docker container on an ARM64 host, with the Pi-only units such as partition resize and cloud-init masked). `pi6529-firstboot.service` ran `validator init` and enabled the service; the validator started, connected to Tor through its relays, reached 4 peers, verified 6529's signed release list and agreed on the network's history; the page answered on 127.0.0.1:7529; `pi6529` welcome, link, status, settings, version, tor-report and `update --check` (both the running-validator path and the offline-verified feed path, plus the newer-release branch with a simulated older install) worked.
- That boot found one real bug, fixed before the tag: 6529's unit has `TimeoutStartSec` 90 s and the clock wait was 120 s, so the service failed on a Pi with no NTP yet. The wait is now 90 s and the drop-in raises the timeout to 5 min.
- The online shape of `validator update check --json` is `{state, current, latest, newer, severity, reason, notes, notes_url, date, commit, download_url, files[]}`; `pi6529 update` reads that first and falls back to the signed feed.

## Left to the builder / open

- Real-hardware boot test on a Pi 4 and a Pi 5: the kernel, firmware, Wi-Fi, mDNS, cloud-init from Imager and the partition resize were not exercised by the container boot.
- The full install path of `pi6529 update` (download, hash check, `apt-get install`) runs only when 6529 publishes a release newer than the one installed; it was reviewed, not run.
- Sigstore verification in `fetch.sh` and `pi6529 update` once 6529 publishes `SHA256SUMS.sigstore.json`.
